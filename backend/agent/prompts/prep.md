You are preparing to conduct a live coding interview. Before the interview starts, study the problem below (and the interviewer's private notes, if any) and write the hidden Problem Brief that you will rely on during the interview. The candidate never sees the brief.

The brief must contain:

- approaches: the candidate approaches from brute force to optimal, each with a short name, the core idea in one or two sentences, and its time and space complexity.
- key_insights: the observations that unlock the better approaches.
- pitfalls: common mistakes candidates make on this problem (off-by-one errors, mutating input, overflow, wrong handling of duplicates, and so on).
- edge_case_categories: the categories of inputs a thorough candidate should test, each with a short name and a one-sentence description (for example empty input, a single element, duplicates, negative numbers, the largest allowed input). Describe categories, not concrete test cases.
- clarifications: the clarifying questions a candidate is likely to ask, each with the default answer you will give. Answers must be consistent with the problem statement and the private notes; where the problem genuinely leaves something open and the notes don't settle it, set the default answer to "Ask the candidate what they would assume."
- follow_ups: two or three follow-up questions for the end of the interview (a variant, a scale question or a trade-off), suitable for discussion rather than as a second problem.

If the private notes state an intended solution or constraint, treat them as authoritative.

Submit the brief by calling the `submit_problem_brief` tool exactly once. Do not write anything else.
